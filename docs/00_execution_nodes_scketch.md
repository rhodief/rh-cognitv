# Sketch of the execution nodes for the AI Agent system

Create a development spec in order to create nodes of execution as follows:

1. **LLMStreamNode**: A node that streams the output of an LLM via stream API. The idea is to have a DI that allow to switch between different LLM provider. This node yields "canonical events" for this application, as long it starts, call deltas for text and object till the end of the stream. After the execution, we end up with a "StreamResult" with consolidated text and object, but also the 'tokens_used', duration and other metadata. If the calling ends up in error, it should brings the error_message, stack_trace, etc, preferably with a canonical error type in order to treat it in the application. This node is the fundament of our agentic systems, and should be as flexible and robust as possible. In addition this node to be a generic stream interface which I can plug different providers, such as OpenAI, Anthropic, Gemini and others, I'd like to work with object rather than just dicts, as SDK often do. You can use pydantic models to leverage both structured data and validation. Create one flag to batch the chunks (text or object) in order to reduce the number of events, it might be useful in order to cast the event in a event broker, so instead of we have something like "Hello|world|!|, |I'm| very| happy| to| help| you" (suppose that each bar is an event) we have a batch of 3 and get something like "Hello world!| I'm very happy| to help you". Default is 1 which is the batch the API naturally cast. For the adapters, use the official SDKs of the providers, check for the most recent version of each one. 

2. **LLMTextNode**: This is the regular text node. It will be used for workflows, so no streaming needed. It should return canonical object with output and useful metadata. Use also pydantic and other ideas applied to LLMStreamNode

3. **LLMStructuredNode**: This is for tool_call. It should receive in addition to the prompt and LLM stuff the list of tools to be called [as pydantic base models]. The idea is that it returns a structured result with the function_name, arguments and other useful information. Place also the optional "choice" param to force a specific tool (many providers have this option), if value is False, it doesnt pass tools at all. By default is "auto" (the model chose whether or not to call)

4. **LLMEmbeddingNode**: This node takes a list of texts and returns a list of embeddings. It should use the same DI idea of the LLM nodes, allowing to switch between different embedding providers. It should return a canonical object with the embeddings, as well as 'tokens_used', duration and other metadata. For the adapters, use the official SDKs of the providers, check for the most recent version of each one.

Those are just the LLM calls, we' gonna have another calls like (function Nodes, FlowNodes as ForEach, MapReduce etc), but not now. I'd like to get my hands durty with these and the we're gonna build are agentic ecosystem on top of it.
